- **Statements on the copy run at a lower CPU priority than the process that started them** (part of #3321). Each SQL statement on the copy runs DuckDB in a worker process of its own. Those workers now start 10 nice steps below their parent (the PostgreSQL router, the MySQL router, or `watch`). While the machine has idle cores nothing changes. When reports fill every core, the parent's own work gets a core first: the short statements a router passes to your database, and capture in `watch`. On an 8-core host profiled with a CH-benCHmark load, the workers took 94 % of the CPU and the short statements passed to PostgreSQL took 3 to 4.7 ms through the router against 1.1 to 1.4 ms directly. The step is relative (a parent at nice 5 starts its workers at 15, never past 19), so it only ever lowers a priority and needs no privilege, in an unprivileged container too. Every thread of the worker gets it, DuckDB's included: the worker is started from a thread of the parent whose priority is lowered first, and that thread ends right after. `BINTRAIL_SQL_WORKER_NICE` sets the step, 0 to 19; `off` or `0` keeps the workers at the parent's priority. In the compose file it is `SQL_WORKER_NICE` in `.env`, passed to the `bintrail`, `router` and `pg-router` services; in the packages, `BINTRAIL_SQL_WORKER_NICE` in `/etc/bintrail/bintrail-console.env`. A worker that cannot be lowered starts at the parent's priority and the log says why once. Linux only. **Upgrading:** nothing to do. The new default applies with the new image or package, whatever compose file is in place, since an unset variable means 10. To turn it off with a compose file from before this change, take the current `docker-compose.yml`, which passes `SQL_WORKER_NICE` through.
