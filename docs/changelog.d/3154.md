- **PostgreSQL router: a statement that returns more rows than the copy's row cap is answered by your PostgreSQL, not run on the copy and refused** (#3154). The copy returns at most `--sql-port-max-rows` rows for one statement (10,000 by default) and refuses a larger result. An expensive statement over that, `SELECT * FROM orders` on a large table for one, was run on the copy, refused when its result passed the cap, and the client got `54000` ("the result has more than N rows"): the copy's work was thrown away, and the same port would have relayed the same rows from the source had the plan been cheap. The port already asks the source for the statement's plan; it now reads the rows the plan says the statement returns, and when they are over the cap the source answers it (`result_over_row_cap` in `/status` and in the `SHOW` of the port's status). This is the MySQL router's rule (#2115). The estimate is used only where it can be trusted: one table read alone, whole or by an index, with nothing checked row by row, under a `LIMIT` or a sort at most. With a filter no index serves, a join, an aggregate, `GROUP BY`, `DISTINCT`, a window or a `UNION` the estimate is a guess (a scan estimated at 221,203 rows that returns 1), so the statement is tried on the copy as before, and still gets the copy's error if it does return more than the cap. **What to expect:** a client that read a whole large table through the port used to get an error after the copy's work; it now gets every row from your PostgreSQL, which runs that read in full. A `LIMIT` at or under the cap keeps the statement on the copy.
