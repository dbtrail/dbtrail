- **The PostgreSQL port returns up to 200,000 rows for one statement** (#3308, #3286). Its row cap was the MySQL port's 10,000, so a report with a larger result was run on the copy and then refused with `54000`, where PostgreSQL alone answers it: CH-benCHmark's Q16 returns about 100,000 rows and failed on every run. The PostgreSQL port's default (`--sql-port-max-rows`) is now 200,000; the MySQL port keeps 10,000. What an answer takes in the router's memory while it is read and sent follows its cells, not its rows (measured at about 160 bytes a cell beside its text), so a result is also held to 1,000,000 cells, rows times columns, cut in the engine as it reads rows; never under 10,000 rows, what any width had before. Q16, 100,000 rows of 4 columns, is 400,000 cells. One answer then takes at most about 220 MB, and the router's memory sum (#3296) now counts that once per statement that can run at once. The rule that sends an expensive statement to the source when its plan estimates a result over the cap (`result_over_row_cap`) keeps 10,000 rows, so every statement it sent there still goes there. `/status` counts the results refused for their size per server, under `result_too_large`: `rows`, `cells`, `bytes` (past 64 MB of text) and `cell_length` (one cell longer than a cell may be). `SQL_PORT_MAX_ROWS` in the compose `.env` (`BINTRAIL_CONSOLE_SQL_PORT_MAX_ROWS`) still sets the row cap of both ports when given. MySQL and MariaDB are unchanged: the engine's cut by cells is off unless the PostgreSQL port asks for it.
