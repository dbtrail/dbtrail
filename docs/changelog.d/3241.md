- **PostgreSQL port: a prepared statement with a `round()` no longer loses PostgreSQL's digits because of one of its arguments** (#3241). The port decides who answers a prepared statement from its text with `$1`, and runs it with each argument written in its place. Two kinds of argument made the statement that ran another one than the statement it had decided on, so a `round()` it had prepared for the copy reached the copy as the client wrote it and was answered the copy's way: `3.5` where PostgreSQL answers `3.50`, `10.50` for `10.5000`. One was a number of more than 18 digits declared as a number (a 19-digit `bigint` key from JDBC's `setLong` or from psycopg, a `numeric` that long): it is now written so that the port reads the statement, and the copy answers with PostgreSQL's digits. The other was an argument inside the `round()` itself, or inside an `avg()` or a `floor()`, when it is a NULL of a declared type, a float or a date (`round(coalesce($1, amount), 4)`): such a statement is now described and answered by the source. Once the copy has refused one run of a prepared statement for its argument, the source answers that statement for the rest of the connection, later arguments the copy would take included. MySQL and MariaDB sources are not affected.
