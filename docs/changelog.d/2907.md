- **Fresh mode no longer answers from the snapshot alone without saying so.** Under concurrent load about 1 % of the SQL port's fresh-mode answers read a table's snapshot without its captured changes laid over it, up to 3 minutes behind, with nothing in the answer to say so; a connection could read a counter that only goes up go back (1319, then 339). Three causes, all fixed. An edit of a server that leaves its index connection alone (its application login on the port, a setting) replaced the server's tails with empty ones; the tails now stay for the same index connection. An update of the tails that failed or ran out of time (a statement's own, in its 2 seconds, or the follower's) dropped every published tail until one succeeded; the last version now stays, older, with the answer's lag saying how much, for up to 15 minutes. And a table whose tail was being built (the first statement over it, the first after a newer snapshot) was read from the snapshot alone; the statement now waits for it, up to 3 seconds, with the follower woken at once. When a table still has no tail, or cannot have one until its next snapshot (a key not made of integers, a changed definition, a table capture does not record, an index with no captured change yet), and for a statement whose tables the port cannot tell apart, a statement on a connection that routes goes to MySQL (counted as `copy_too_old`), and one on a connection that does not route is answered from the snapshot with a warning that says so (`SHOW WARNINGS`). The copy also never answers a connection with less of the index than an earlier answer of the copy on that connection held. A statement waiting for a tail holds its place among the statements that run on the copy at once.
