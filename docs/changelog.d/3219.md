- **PostgreSQL port: three common report shapes are answered by the copy instead of your PostgreSQL** (#3219). Each was sent to the source for a rule drawn wider than what differs, and each is now measured against PostgreSQL answering the same, row for row:
  - **A series by day, month or year over a `timestamp with time zone`**: `date_trunc('day', o.created_at) ... GROUP BY 1 ORDER BY 1`. Only a `timestamp` column passed, and only written without its table. A `timestamptz` column passes too, with or without its table; the copy answers in a session in UTC, as it does everything else, so the day is the UTC day on both sides. The field name (`'day'`) no longer counts as text of the statement, which had sent the `ORDER BY 1` of such a series to the source.
  - **A `char(n)` column as the key of `GROUP BY`**: `SELECT status, count(*) FROM t GROUP BY status`. Every value of a `char(n)` is padded to the same length, so the copy makes the same groups. The key must be the column alone, in a statement that is one `SELECT`; a `bpchar` without a length still goes to the source.
  - **A sort key that is a `sum`, a `count` or another call that never answers text**, in a statement that also reads a text column: `ORDER BY sum(amount) DESC`, a `rank() OVER (... ORDER BY sum(amount) DESC, id)` in a subquery joined to a table with names. The statement was sent away as if it sorted text.

  Two things of the same family are not changed, because the copy does not answer them the same. `ORDER BY` of a `char(n)` or any text column is still the source's: PostgreSQL sorts text by the database's collation, the copy by bytes, so `GROUP BY status ORDER BY status` goes to the source and `GROUP BY status ORDER BY count(*) DESC` stays. And `avg()` of a `numeric` that is not inside a `round()` is still the source's, even when it is only compared: the copy's average is a double precision, and a value that equals the average exactly on PostgreSQL can fall on the other side of it on the copy.
