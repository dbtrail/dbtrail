- **PostgreSQL fresh mode: a table below `REPLICA IDENTITY FULL` keeps its recent changes when one of them leaves a large value untouched** (#3049). For an UPDATE that does not touch a large value stored out of line, PostgreSQL does not send the value unless the table is at `REPLICA IDENTITY FULL`. The scheduled snapshot update already read it from the table's copy (#3009); the recent changes fresh mode lays over the copy took it only from an earlier change of the same row they still held, and otherwise the table lost them until its next snapshot and its statements read the snapshot alone. They now read the value from the snapshot the statement reads: the table delta beside the file first, then the file, by key, one read per table for all its rows that wait, counted against the memory fresh mode may hold (`BINTRAIL_SQL_TAIL_MAX_BYTES`). After a snapshot update the newer snapshot is the one read. A row the snapshot does not hold, a NULL or an empty text there (never a value PostgreSQL leaves unsent), a snapshot that cannot be read, and values that do not fit the memory budget on their own end that table's recent changes until its next snapshot, with the reason in the log; a NULL is never written in the value's place. With no room left in the budget, or no time left in the update, the read waits for a later update and the table keeps what it last had. Nothing captures such a change yet (capture still skips tables that are not at FULL), so no answer changes today. MySQL and MariaDB servers are not affected: the step is taken only for a PostgreSQL server.
