- **The PostgreSQL router works out each statement's threads from the machine unless they are set** (part of #3321). `--threads` (`BINTRAIL_PG_ROUTER_THREADS`, `PG_ROUTER_THREADS` in the compose `.env`) now takes a number from 1 to 16 or `auto`, and `auto` is the default. With `auto`, the vCPUs the router may use are shared among the statements that can run on the copy at once (`--workers` plus the one kept for short statements), rounded up. The vCPUs are what the Go runtime counts for the process (`GOMAXPROCS`): the CPUs it may run on and a container's CPU limit, rounded up (a limit of 1 or 1.5 CPUs counts as 2 on a larger machine). It is worked out once, at start. The start-up lines say the number and where it came from, for example `3 threads (auto at start: 8 vCPUs over 3 statements at once)`. vCPUs and not cores, and rounded up, because the reports are CPU-bound. On a 16 vCPU Intel machine with two hyperthreads per core, 3 reports at once answered 72.8 a minute at 6 threads each and 58.8 at 3. On Graviton and AMD a little over the vCPUs cost nothing measurable. The router's own statements stay fast because the workers run at a lower CPU priority, not because cores are left free. **What changes for an installation that does not set the threads:** with the default 4 workers, nothing on 8 vCPUs (2 threads, as before); 4 threads on 16 vCPUs instead of 2; 1 thread instead of 2 on 4 vCPUs or fewer. With `PG_ROUTER_WORKERS=2` and 8 vCPUs, 3 threads instead of 2. **A number that was set is used exactly as before**: `PG_ROUTER_THREADS=4` stays 4 whatever the machine. The compose file already passes an empty value when `.env` sets none, so it needs no change. **Upgrading:** to keep 2 threads per statement whatever the machine, set `PG_ROUTER_THREADS=2` in the compose `.env` or `BINTRAIL_PG_ROUTER_THREADS=2` in `/etc/bintrail/bintrail-console.env`. More threads per statement also let it use more memory within its `--sql-memory`; on a large machine, a large join may then spill or fail where it fit before.
