- **PostgreSQL: a publication that does not publish `TRUNCATE` is now said, with the statement that fixes it** (#3108). A publication created `WITH (publish = 'insert, update, delete')` (`pg_publication.pubtruncate = false`) sends nothing for a `TRUNCATE`, so DBTrail never learned that a table was emptied: the removed rows stayed in the copy and came back in every rebuild, and nothing said so. A new check, **Publication publishes TRUNCATE**, warns in `bintrail-pg doctor`, `server add`, Test connection and Start; capture logs it once when it starts, and the PostgreSQL health card shows it on every reading (so a publication changed while capture runs is seen there, and logged when first seen; a failed read shows "could not check"). It is a warning and not a refusal: every insert, update and delete is still captured. It prints `ALTER PUBLICATION <name> SET (publish = 'insert, update, delete, truncate');`, which keeps the publication's tables and its other options such as `publish_via_partition_root`; DBTrail does not change the publication. The refusal for a publication missing insert, update or delete now suggests the same statement instead of recreating the publication without `truncate`.
