- **A PostgreSQL capture records when it was last caught up with its source** (#2845). The web interface and the router say how far behind the source an answer is from a stamp the capture leaves in the index (`stream_state.caught_up_at`). The MySQL capture wrote it; the PostgreSQL capture did not, so a PostgreSQL server never showed as caught up there and its lag was always the copy's whole age. It now does: with each health poll (every 30 seconds) the capture asks the source how far its WAL is flushed, and if it has received the source's changes up to that point within a second of asking, the moment it asked is stamped at the next checkpoint. A capture that is more than a second behind stamps nothing, and shows as behind. A lost replication slot and `bintrail-pg reset` remove the stamp. If the source's position cannot be read, the capture says so once in its log and writes no stamp. One more `SELECT` on the health poll's connection; nothing is installed in the source.
