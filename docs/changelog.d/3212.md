- **A PostgreSQL capture that lost its capture lock no longer writes when it stops** (#3114). When a process stopped because it no longer held the lock, it still wrote the rows it had received and saved its position, possibly over the position of the process that holds the lock now. That could leave duplicate rows in the index or make the new owner resume from the wrong place. It now stops without writing rows, position, schema records or source health, and without confirming anything to the replication slot. What it had not saved is sent again to whoever captures next. Each capture run also records itself as the owner of the index when it starts, and a position save from an earlier run that reaches the index late is refused, so it can no longer replace the position the new run is working from. A capture that stopped before its first save no longer indexes those rows twice when they arrive again, and says how many it skipped. MySQL and MariaDB sources are not changed.
