- **The MySQL port prints a `FLOAT` and a `DOUBLE` cell as MySQL does** (#2829). The copy sent the value it computes with as it was: `3.14` stored in a `FLOAT` came out as `3.140000104904175`, `0.3333333` as `0.3333333134651184`, and a `DOUBLE` `1e38` as `1e+38` and `1e-10` as `1e-10` where MySQL sends `1e38` and `0.0000000001`. A client that reads the cell as text (the mysql command line, a driver's `getString`) saw the difference. The copy now prints a `FLOAT` with six significant digits and a `DOUBLE` with the shortest exact text, in MySQL's fixed and exponent forms, and declares both columns with MySQL's decimals (31); measured against MySQL 8.0.46 on 9,000 values. A prepared statement still gets the exact value, so two `FLOAT`s MySQL prints alike stay two values there. A column MySQL prints with fixed decimals or zero padding (`DOUBLE(10,2)`, `FLOAT(7,2)`, `ZEROFILL`) cannot be printed that way by the copy: under routing a statement that names one, or a star over its table, now goes to MySQL (a `DOUBLE(10,2)` was answered by the copy before, as `0.1` for MySQL's `0.10`), and the port without routing answers a statement over its table from the copy with a warning (code 1105, read with `SHOW WARNINGS`) that names the column and says its values are written without those decimals. NaN and an infinity, which MySQL never sends, are refused by the copy too (error 1690 without routing; MySQL answers under routing).
