- **PostgreSQL port: a statement that compares a `char(n)` column is answered by PostgreSQL, not by the copy with other rows** (#3068). PostgreSQL pads a `char(n)` value with blanks and ignores them when it compares; the copy holds the value as text with its blanks and compared them, and the port did not know the column was a `char(n)`. So `WHERE code = 'ab'` on a `char(5)` column gave 3 rows on PostgreSQL and 0 through the port, `length(code)` 2 and 5, `code || 'x'` `abx` and `ab   x`, with no error. The port now reads each column's type on the source from the snapshot and sends to the source every statement that uses a `char(n)` column where its blanks count: any comparison, a join's condition, `GROUP BY`, `ORDER BY`, a function, `||`, a cast, a `CASE`, an aggregate, a set operation, and a `*` that stands for it inside a subquery or a `WITH`. What stays on the copy is the column as a whole item of the select list of one plain `SELECT` (`SELECT id, code FROM t WHERE id = 7`, `SELECT * FROM t WHERE id = 7`), where both sides write the same padded value, and every statement on a table without such a column, which is decided as before. A `bpchar` without a length, and the text columns of a table whose snapshot predates recorded column types, are treated the same and a little more strictly. **A server with no forwarding user, or one that hides tables or columns, now refuses such a statement (`0A000`, naming the column) where it used to answer it with other rows.** Not told apart, and still compared with its padding: a domain over `char(n)`. The console's SQL card and the `sql` tool are unchanged.
