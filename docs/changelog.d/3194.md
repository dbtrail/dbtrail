- **PostgreSQL: a snapshot update no longer rewrites a changed table in full by default** (#3194). An update of the copy of a PostgreSQL source wrote every table that changed again, whole, however small the change. It now keeps the table's file as it was (a hard link, no extra disk) and writes the changes of the update beside it, in small files named `<table>.<six digits>.pgdead` and `.pgnew`. The table is still written in full when its changes pass a quarter of its rows, when its file is older than the index is sure to reach back, or when the delta cannot be written. Everything that reads the copy on this machine reads those files with the table's file: the SQL page, the PostgreSQL port, the AI connection, fresh mode, the views pinned to a snapshot, the views in a snapshot download and in S3, the upload and its integrity checks. **What can behave differently:** a views file that follows later snapshots, which is what `bintrail views` writes unless given `--pin-snapshot`, and one with relative paths for a folder that was moved, cannot look beside a table's file when it is written; for a PostgreSQL table with a delta it refuses when read, with a message that says to read the table through DBTrail or to generate the views pinned to a snapshot (`bintrail views --pin-snapshot`). It no longer happens only to whoever turned the switch on. **To turn it off:** `BINTRAIL_PG_TABLE_DELTAS=0` (or `false`, `no`, `off`), or `pg-table-deltas = off` in `dbtrail.cnf`; every changed table is then written in full, as before. An unset or unreadable value means on. MySQL and MariaDB sources do not read the switch and are unchanged (their table deltas are `--table-deltas` / `baseline-table-deltas`, as before).
- **PostgreSQL: a read of one row at a past moment checks for a TRUNCATE from where a table file with a delta beside it really starts** (#3194). A table published as its previous file and a delta holds the rows as they stood when that file was written, before the snapshot folder it sits in. Every read of one row at a past moment (`bintrail reconstruct` and `--baseline-only`, the time travel of the MySQL-protocol shim, the console, the MCP `reconstruct` tool, `verify`) took the folder's time as the snapshot's, so a TRUNCATE between the two, and a capture gap there, were not seen, and `--baseline-only` printed the file's row under the folder's time. For such a file they now take the earliest moment its rows can stand at: the earlier of the time the file was written and the bound its footer records of how far back its changes reach. That is the full read's own time beside a full read, and the bound an update recorded beside a file it wrote in full, where the time is that update's clock. This is what they already did with a MySQL table delta, from its chain's start. A delta beside a file that records no time or no readable bound, or a store in S3 that cannot be asked whether one is there, is refused, with what to do. MySQL and MariaDB reads are unchanged, and in S3 they make no request more than before: the listing they already made says whether a PostgreSQL delta is there.
