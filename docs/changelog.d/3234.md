- **In fresh mode, a statement over a table that already has recent changes to read no longer waits for an update of them, and may answer from the version before that update** (#3234). Every statement on the MySQL and PostgreSQL ports used to wait for any running update of the copy's recent changes, however long it took; with an update held for 4 s, a report went from 4 s to under 65 ms. The price, on both ports: during an update an answer may come from the version before it, with no notice, usually seconds behind and a minute or more in a long update. On the MySQL port, with `BINTRAIL_SQL_FRESH_WAIT` on, a statement waits for the running update first. A write captured before that update began is read; a write made during it needs the next update to finish within the wait, or the statement answers from the version before it. PostgreSQL has no such switch; a connection the source already answered waits for the copy or goes to the source, which does not cover an application that writes on another connection. A table with no version yet still waits for the running update, for at most half of the statement's time limit, and then goes on: your database answers it, or the copy does and says it read the snapshot alone. While the index holds no captured change at all, the first change can be missing from statements that run during the update that brings it.
