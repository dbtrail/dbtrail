- **A PostgreSQL snapshot update follows a row whose primary key changed** (#2760). An `UPDATE` that changed the primary key made the update refuse the table, and the schedule then read the whole table from the source again. It is now applied as a delete of the old key and an insert of the new one, as on MySQL and MariaDB, ordered against the other changes of both keys by commit LSN. It still refuses, with the reason in the message, when the change cannot be proven whole: no commit LSN in the index, an old row captured without every column, a key column missing from either row, a stored key the old row does not spell, or an old row with NULL in every column outside the key when the new row has a NULL there too (it cannot be told from a row captured with the key only). It also refuses when, inside one transaction, a key receives a row and is changed again later with a key change among those changes: with a `DEFERRABLE` primary key that is several rows shifting onto each other's keys (`UPDATE t SET id = id + 1`), which the captured changes do not tell apart from one row moved several times. The last change of a PostgreSQL row is now chosen by commit LSN too, where it was the order the changes were read in; the two differ only when two commits carry times in the other order than their LSNs. MySQL and MariaDB are not changed.
