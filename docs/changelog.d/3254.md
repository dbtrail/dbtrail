- **The PostgreSQL port serves a server only when it can forward** (#3254). A connection that could reach only the copy got, for some statements, rows PostgreSQL would not return, with no error. Now a client of a PostgreSQL server the port cannot send to its PostgreSQL is refused at login with `FATAL` `08004`, naming the server, the reason and both ways to serve it: forward as the user DBTrail connects with (`server forward-user <server> --capture-account`, or the box in the server's form), or give it a forwarding user of its own. Where a person is asked, forwarding as the user DBTrail connects with is offered first: the box in the form of a new PostgreSQL server is ticked, and Enter is yes at `server add` on a terminal; a script that says nothing still gets no. The checks, and saving the yes, warn when that user is a superuser or can bypass row-level security, with the statements for a role that only replicates and reads. A saved forwarding user that is the user DBTrail connects with is used as that account once the server says yes, instead of being refused. Capture, snapshots, the web interface and the MySQL port are unchanged for every server; the daemon names at boot each server the port does not serve, its Overview has a card, and `GET /api/servers` has `pg_port_refused`.
  - **Before you upgrade**: a PostgreSQL server with no forwarding user and without a yes about the user DBTrail connects with stops being served by the PostgreSQL port: its clients get the error above at login. Run `bintrail-console server forward-user <server> --capture-account` (or tick the box in the server's form), or set a forwarding user of its own, before or right after the upgrade. Capture of that server keeps running either way. A server that already forwards, with the yes or with a forwarding user of its own, needs nothing.
  - **Before you upgrade**: Statements the port forwards to the source do not leave an audit record yet: with this release every PostgreSQL server the port serves forwards part of its statements, so fewer of the port's reads are recorded, and those reads run on the source as the forwarding account. This is fixed later (#3256).
  - **Known, fixed after this release**: on a server that forwards, a statement the port cannot read as a read (`SELEC 1`) is refused with `25006` (read-only) instead of PostgreSQL's `42601` (syntax error).
  - **Known, fixed after this release**: on a server that forwards as the user DBTrail connects with, a misspelled table gets a long `0A000` that the port refused to send it, instead of PostgreSQL's `42P01`.
  - **Known, fixed after this release**: on that path `PREPARE`, `SELECT ... FROM ONLY t`, `EXPLAIN SELECT` and `DECLARE ... CURSOR` are refused instead of answered.
