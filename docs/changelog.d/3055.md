- **Adding the first server turns the MySQL port on after the monitor login, a password or Engine Routing was saved first** (#3055). Adding the first server turns the port on, with Engine Routing on, unless somebody turned it on or off before. DBTrail took the port's settings file existing as that choice, and the file is also written by saves that choose neither: the monitor login (`PUT /api/flashback/monitor-login`), a password made ahead (`dbtrail port new-password`) and Engine Routing alone (`dbtrail port routing on|off`). After any of them, `dbtrail server add` for the first server left the port off and said `The MySQL port is off, as it was saved`; and a first `dbtrail port on` started with Engine Routing off.
  - **What happens now.** The first server turns the port on in those cases too, and what was saved is kept: the monitor login, the password (none is made; the command says the port takes the one made before, which is not shown again) and Engine Routing if it was turned off (it stays off, and the command says so). A first `dbtrail port on` starts with Engine Routing on unless it was turned off before.
  - **What does not change.** A port that was turned off stays off however many servers are added. Only the first server turns it on, and not from a session that may not change settings or that has a data access policy.
  - **After an upgrade.** The settings file now says when nobody has chosen yet (`port_not_chosen: true`, `routing_not_chosen: true`). A file written by 0.137.0 or older does not say, so it is read as a port that was turned off: if the first server is added after the upgrade and the port stays off, turn it on with `dbtrail port on`.
