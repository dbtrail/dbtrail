- **The PostgreSQL port no longer answers from the copy a table changed on the source since its snapshot** (#3293, closes #3251). PostgreSQL does not announce an `ALTER TABLE` to capture, so after a change no write followed (a column retyped, its modifier changed, added, dropped or renamed, the table dropped and created again) the copy answered with the snapshot's columns, and rows PostgreSQL would not return, with no notice, until the table's next snapshot. Before the copy answers a statement, the port now reads from the source's catalog, as the forwarding user and never a row of a table, the OID and columns of the tables the statement reads, kept one second per table, and compares them with what the snapshot recorded. A difference sends the statement to the source (`copy_shape_differs` in `/status`), heavy statements included; on a server that hides tables or columns it is refused with `55000`, and the client is told the table changed, never which columns. **Behavior change:** when the source cannot be asked for those columns (it is down, or does not answer within two seconds), a statement that reads a table is refused with `55000` (`copy_shape_unchecked`) instead of being answered by the copy; a statement that reads no table is still the copy's. Not covered: a rewrite that keeps every column's type (`ALTER COLUMN n TYPE int USING n + 1` on an `int` column) changes values and no column, and still shows the old values until the table's next full read.
