- **A read-only MySQL port marks the session read-only on the source too** (#3093). Read-only mode was enforced by reading each statement's text, so a write the text does not show (a stored function a `SELECT` calls) was forwarded and ran, bounded only by the forwarding account's grants. Now every connection a read-only port opens to the source starts with `SET SESSION TRANSACTION READ ONLY`, and the source itself refuses a write with its error 1792, whatever the statement's text. What would take that back is no longer sent to the source: the port answers `SET SESSION TRANSACTION READ WRITE`, `SET TRANSACTION READ WRITE` and a `SET` of `transaction_read_only` (`tx_read_only`) with OK itself, so drivers and pools that switch a connection back from read-only see no error, and writes stay refused. `START TRANSACTION READ WRITE` now gets error 1290 on a read-only port, as a MySQL server with `read_only=ON` answers it; it was forwarded before. `SELECT @@session.transaction_read_only` on a read-only port now answers 1. If the source refuses the first statement, the connection to it is not opened and the log says why. The screen was also checked against the server's own reading of a statement (comments, quotes under each `sql_mode`, escapes, several statements in a packet, prepared statements), with a table of cases and with generated text run on the server: nothing it allows changed a table.
