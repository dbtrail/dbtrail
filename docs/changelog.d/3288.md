- **The PostgreSQL port runs a statement that ran out of memory on the copy once more with its joins in the order written** (#3288). Before, a statement the copy failed with `Out of Memory Error` went straight to the source (`copy_refused`). Now the copy runs it again with join reordering off, in the same worker slot and within what is left of the statement's time, and answers it when that fits: CH-benCHmark Q9 over fresh-mode views ran out of a 2 GB worker after 21 to 59 s in the engine's order, then took 42 s on the source, and answers in 5.5 to 7.9 s in the order written. It is not run again when the first run already used the order written, when less than a second is left, or when the client cancelled or left. When the second run fails too, the statement goes to the source as `copy_refused_after_written_order`. `/status` counts both outcomes under `join_checks` (`oom_retry_written_order_ok`, `oom_retry_written_order_failed`), and each retry is one `INFO` line with the time of each run. The MySQL port and the SQL page are unchanged.
