- **The PostgreSQL port runs a statement that ran out of memory on the copy once more with its joins in the order written** (#3288). Before, a statement the copy failed with `Out of Memory Error` went straight to the source (`copy_refused`). Now the copy runs it again with join reordering off, in the same worker slot and with the same views, within what is left of the statement's time and at most half of what is left of the client's `statement_timeout`, and answers it when that fits: CH-benCHmark Q9 over fresh-mode views ran out of a 2 GB worker after 21 to 59 s in the engine's order, then took 42 s on the source, and answers in 5.5 to 7.9 s in the order written. It is not run again when the first run already used the order written, when less than a second is left, or when the client cancelled or left. When the second run runs out of memory or time too, the statement goes to the source as `copy_refused_after_written_order`; another error of the second run is answered as that error. `/status` counts every outcome under `join_checks` (`oom_retry_written_order_ok`, `_failed`, `_other_error`, `_skipped_<why>`), and each is one `INFO` line with the time of each run. The MySQL port and the SQL page are unchanged.
