- **PostgreSQL: a table that is not at `REPLICA IDENTITY FULL` is captured. `FULL` is needed only for undo** (#3027). Until now capture skipped every change of such a table, `doctor` and `server add` failed on it, and `status` reported capture as degraded. Now the table is captured and everything works on it (history, the copy and the SQL it answers, snapshots and their scheduled updates) except undo of its `UPDATE` and `DELETE`: PostgreSQL sends only the key of the row such a change started from, so `recover` refuses the window with a message that names the table and the `ALTER TABLE ... REPLICA IDENTITY FULL` to run (it takes effect for later changes, and the table then writes more WAL). Undo of an `INSERT` works. In the index the earlier row of such a change holds its key and marks every other column as not captured, never as NULL; a large value an `UPDATE` did not touch and PostgreSQL did not send is marked as such in the new row, and a snapshot update takes it from the row's earlier change or from the table's previous snapshot file.
  - **`doctor`, `server add` and Start**: the check **REPLICA IDENTITY FULL** is a warning, no longer a failure, so a server with such tables is added and started and `doctor` exits 0. It lists the tables and the statement for each. The web interface's Status page shows `N tables without undo` in amber, and the add-server form says `FULL` is optional.
  - **Still not captured, each under a reason of its own while the other tables go on**: a table whose replica identity leaves a primary-key column out (in practice `REPLICA IDENTITY USING INDEX` on an index without the primary key), skipped under `replica_identity_index_without_primary_key` and reported by a new failing check, **Replica identity holds the primary key** (a server is not added or started while it fails), with `ALTER TABLE ... REPLICA IDENTITY DEFAULT` (or `FULL`) to run; and a table whose primary key is `DEFERRABLE`, skipped under `primary_key_deferrable`. The deferrable-key check ran only when capture started; it now also runs each time PostgreSQL describes a table, so a key rebuilt as deferrable while capture runs is seen without a restart. It reads the catalog as it is when capture reads a change, which the docs state as its limit.
  - **Partitioned tables published through their root** (`publish_via_partition_root`): `REPLICA IDENTITY` is set per partition, and PostgreSQL labels the earlier row by the parent's setting while it holds what the partition logged. A parent at `FULL` over partitions that are not sent key-only rows labeled as whole ones, which were stored with NULL in every column outside the key. Capture now asks the catalog and stores such rows as what they are; `doctor` lists the partitions that need the statement.
  - **Not covered, as documented**: `verify` on a table that is not at `FULL`; a read of one row at a moment (`AS OF`, `_flashback`, `_snapshot`, `reconstruct`) through a change that left a large value untouched, which answers with an error that names the column. The reason `replica_identity_not_full` is no longer recorded; what an index already holds under it stays.
