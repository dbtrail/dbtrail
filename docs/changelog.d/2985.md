- **The PostgreSQL port sends to the copy only what is expensive on the source** (#2985). With a forwarding user, every statement the copy answers as PostgreSQL does went to the copy, reads by a primary key included; the copy has no index, so `SELECT ... WHERE id = $1` on a table of 2 million rows took 15 seconds there, queued behind one worker, against about a millisecond on PostgreSQL. The port now asks the source for the statement's plan first (`EXPLAIN (FORMAT JSON)`, `GENERIC_PLAN` for a prepared statement with parameters) and sends it to the copy only when the plan's Total Cost is 50,000 or more, or a sequential scan in it is estimated at 1,000,000 rows or more; otherwise the source answers it (`cheap_plan` in `/status`). An `EXPLAIN` the source refuses sends the statement to the source, which answers with its own error (`explain_failed`). The thresholds are `--cost-threshold` and `--scan-rows` of `pg-router` (`BINTRAIL_PG_ROUTER_COST_THRESHOLD`, `BINTRAIL_PG_ROUTER_SCAN_ROWS`; `PG_ROUTER_COST_THRESHOLD` and `PG_ROUTER_SCAN_ROWS` in the compose `.env`). On PostgreSQL 15, which has no `GENERIC_PLAN`, a prepared statement with parameters goes to the source. Measured under 50 clients, two things this needed are part of it. A statement that finds the port's connections to the source all taken (`--max-source-connections`, 16) now waits for one to be given back, up to 30 seconds or its `statement_timeout`, as a statement waits in line for the copy; before, it was refused at once with `53300`, which 92% of the bench's statements got. And a connection the source answered waits for the copy to catch up with it: the copy, a second or two behind, had read a counter go back (37413, then 37405) on one connection. A statement for the copy on such a connection now reads where the source's WAL stands and waits, up to 6 seconds and never past its `statement_timeout`, until capture has saved that position and the copy's recent changes are up to date after it, then the copy answers; when capture cannot get there in time, the source answers at once (`copy_too_old` in `/status`) and the copy runs nothing. Measured in fresh mode with the counter written every 20 ms: the copy answered 100 of 100 such reads, none went back, and 10 of 10 on a quiet source. A table read from its snapshot alone goes to the source on such a connection. This applies to every connection with a forwarding user, so one that ran a transaction block on the source waits for the copy after its `COMMIT` too. A connection also remembers the source's verdict on a statement shape for a minute, when every value in it is compared with `=` and the plan is ten times from the thresholds, so a read by key with another key is not asked about again. The source's position is asked right behind every statement it answers, so the wait needs no connection to the source; when no position after the source's last answer is known, the source answers (said once a minute in the log), and no clock of the source is compared with the router's. When the source cannot be reached, a statement the copy can answer is answered by the copy with a NOTICE (`source_unreachable`), as before routing by plan. A cancel request ends the wait for a connection to the source, and one `statement_timeout` covers every wait of a statement. A verdict for the copy is not remembered, so a table dropped and made again on the source is not read from the copy's old rows. The rule holds table by table: the port keeps which tables the source answered a connection about, and only a statement that reads one of them waits for the copy or goes to the source; one that reads other tables is answered by the copy at once, so two answers on one connection about different tables can be of different moments (the source's of now, the copy's a second or two behind). Which tables a statement read is confirmed by the source itself, with one catalog query sent in the same write as the statement; whenever that cannot be proven (a view, a partitioned table or an inheritance parent, row-level security, a function not known to read no table, a function in `FROM`, `LATERAL`, a cursor, several statements in one text, a database with an operator or cast written in SQL, and the other cases `docs/postgres.md` lists), the statement counts as having read every table and the rule is the connection's, as before. While it waits a statement holds its connection to the port and nothing else: no worker of the copy and no connection to the source.
