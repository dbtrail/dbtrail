- **PostgreSQL port: a server can forward with the account DBTrail captures with, once somebody says yes** (#3061). A server needed a second role on its source before the port sent anything there. `bintrail-console server forward-user <server> --capture-account` saves a yes (`--no-capture-account` takes it back; the API is `PUT /api/servers/{id}/route` with `{"capture_account": true}`). With it, and no forwarding user of its own, the PostgreSQL port forwards with the capture role, read-only, and sends only a `SELECT` whose every table is a table of the copy: the text is read whole, your PostgreSQL confirms before the statement that each name is a plain table and that nothing of a user's runs in it, and each table must be one the copy holds by schema and name. Anything else answers `0A000` and nothing of it is sent. No answer is no: an existing or upgraded server does not start forwarding. An edit that points the source at another user or host takes the yes back. A forwarding user, when set, is used instead.
- **MySQL port: the same yes is saved and not acted on yet** (#3061). The MySQL port cannot yet show which tables a statement reads, so it keeps forwarding only with a forwarding user of its own, and `SHOW ROUTER STATUS` says so.
- **Both ports' status statements name the account they forward with** (#3061): `forwarding_account` in `SHOW ROUTER STATUS` and `SHOW dbtrail.router_status` (`forwarding user <name>`, `capture account, read-only, tables of the copy only`, or `none` with the reason), and in the PostgreSQL router's `/status`.
