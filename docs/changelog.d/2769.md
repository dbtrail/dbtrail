- **The PostgreSQL port applies session settings, answers `SHOW` and `version()`, and cancels a running statement** (#2769). `bintrail-console pg-router` used to answer every `SET` with `SET` and change nothing, refuse `SHOW`, answer `version()` with the copy engine's version (so SQLAlchemy, and Superset with it, could not connect), ignore the settings a driver sends when it connects (JDBC sends its JVM's `TimeZone`), and close a cancel request without stopping anything. Now `TimeZone`, `search_path` (one schema of the copy), `statement_timeout`, `application_name` and `client_min_messages` are applied, from `SET` or from the connection parameters; the settings that change nothing the port answers (`extra_float_digits` 1 to 3, `DateStyle` `ISO, MDY`, `client_encoding` `UTF8`) are taken; and a value that would change an answer the port does not apply, or a name it does not take, is refused with the reason, never acknowledged and ignored. `SHOW`, `RESET`, `SET LOCAL`, a `SET` undone by `ROLLBACK`, and the `ParameterStatus` a client is sent read as on PostgreSQL 16, checked statement by statement against it; under each zone tested a `timestamptz` and what the copy computes from one read the same as on the source, in text and in binary, except one case: the copy's engine reads Europe/Amsterdam before 1937 without its local mean time (+00:19:32), so a cast or `date_trunc` of such an instant there differs from the source by those minutes. Each connection gets a process number and a random secret key, and a cancel request with both, in clear text or over TLS, stops that connection's statement with `57014 canceling statement due to user request` and leaves the connection open, checked with `psql`, JDBC, psycopg and `pgx`. `infinity` and `-infinity` in a `date` or timestamp column read as on the source in binary too (the ends of the count PostgreSQL sends), where the port refused them. The catalog queries tools send to list tables (`\d`, JDBC `getTables`) are not answered yet.
