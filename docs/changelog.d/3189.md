- **PostgreSQL: a table that is not at `REPLICA IDENTITY FULL` is no longer captured, and `doctor` fails on it** (#3189). This reverses what 0.138.0 did (#3027), where such a table was captured with the earlier row of each `UPDATE` and `DELETE` holding its key only. Now a table at `DEFAULT`, `USING INDEX` or `NOTHING`, or a partitioned table with a partition that is not at `FULL`, has every change dropped (its `INSERT`s included) and counted under `replica_identity_not_full`, while the other tables keep being captured; `status` reports capture as degraded and names the table, and the log gives the `ALTER TABLE ... REPLICA IDENTITY FULL` to run. After that statement, capture of the table resumes by itself, with no restart. The `doctor` check **REPLICA IDENTITY FULL** is a failure again, with one statement per table and partition, so `server add` and the web interface's Start do not add or start a server while such a table is in the publication; a capture that is already running, or that the daemon resumes when it restarts, goes on and skips the table alone. On PostgreSQL 18, `doctor` prints `ALTER PUBLICATION ... SET (publish_generated_columns = stored)` before the `ALTER TABLE` for a table with a `STORED` generated column the publication does not publish, and no `ALTER TABLE` at all for one with a `VIRTUAL` column, which cannot be at `FULL` while it is published and so cannot be captured. A scheduled update of a PostgreSQL snapshot is now refused when capture dropped changes of one of its tables since that table's rows were read from the source (`refused-gap`, naming the table): before, the update was built from the index without those changes and published the table's old rows as current. The add-server form, the Status page, the command help and `docs/postgres.md` say `FULL` is required.
  - **Upgrading from 0.138.0 with tables that are not at `FULL`:** capture keeps running and takes the other tables; the changes of those tables from the upgrade on are not recorded. What 0.138.0 recorded of them stays in the history, and undo still refuses its `UPDATE`s and `DELETE`s. Their copy is no longer brought up to date from the index: fresh mode leaves them out, and once one of their changes is dropped, the server's scheduled snapshot updates are refused until a full read. To capture such a table again, run the `ALTER TABLE` that `bintrail-pg doctor` prints (on each partition too, for a partitioned table), then a full read. A server that is stopped cannot be started from the web interface until then.
