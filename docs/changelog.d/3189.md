- **PostgreSQL: a table that is not at `REPLICA IDENTITY FULL` is no longer captured, and `doctor` fails on it** (#3189). This reverses what 0.138.0 did (#3027), where such a table was captured with the earlier row of each `UPDATE` and `DELETE` holding its key only. Now a table at `DEFAULT`, `USING INDEX` or `NOTHING`, or a partitioned table with a partition that is not at `FULL`, has every row change dropped (its `INSERT`s included; a `TRUNCATE` of it is still recorded) and counted under `replica_identity_not_full`, while the other tables keep being captured; `status` reports capture as degraded and names the table, and the log gives the `ALTER TABLE ... REPLICA IDENTITY FULL` to run. After that statement, capture of the table resumes by itself, with no restart. A table created in a `FOR ALL TABLES` publication starts at `DEFAULT`, so it is skipped until that statement: run it right after the `CREATE TABLE`.
  - **`doctor`, `server add` and Start**: the check **REPLICA IDENTITY FULL** is a failure again, with one statement per table and partition, so a server is not added or started while such a table is in the publication; a capture that is already running, or that the daemon resumes when it restarts, goes on and skips the table alone. The check, and the PostgreSQL 18 generated-columns check, look only at the tables the server captures (its schemas and tables), as capture does. On PostgreSQL 18, `doctor` prints `ALTER PUBLICATION ... SET (publish_generated_columns = stored)` before the `ALTER TABLE` for a table with a `STORED` generated column the publication does not publish, and no `ALTER TABLE` at all for one with a `VIRTUAL` column, which cannot be at `FULL` while it is published and so cannot be captured.
  - **The copy**: a scheduled update of a PostgreSQL snapshot no longer rebuilds from the index a table whose changes capture dropped since its rows were read from the source. Before, it laid the changes the index has over the table's file and published old rows as current. Now it publishes that table as the last update left it, the same file with its footer, and brings the other tables up to date. Where it shows: the daemon logs a warning for each such table (`table published as its last read left it, not brought up to date`, with why), and the web interface's Status page lists it among the tables NOT captured; the snapshot pages still count it among the tables reused unchanged, and show it as `reused unchanged`; where the file cannot be published again as it is (a snapshot read from S3, carry-forward off), the update is refused, naming the table. Whether a table's copy holds every change since its rows were read is decided against the capture's record of dropped changes: by WAL position for a file that is a full read of the source, and, for a file an update built, by the time of its last read of the source with a five-minute margin toward refusing (an update's floor can be past a drop the capture had not saved yet). With #3191, which ships with this, the PostgreSQL port sends a statement that reads such a table to the source (`table_not_captured`).
  - **Reads at a past moment**: single-row `reconstruct` (the command line, the MCP tool, the web interface) and, on the PostgreSQL port, `AS OF`, `_snapshot` and `_flashback` refuse such a table with a message that says why and what to run (`reconstruct --baseline-only` too, when given the index; without one, with one it cannot read, or with one that is not this PostgreSQL capture's, it says the snapshot was not checked and reads it all the same); `verify`, live and between two snapshots, reports it as not compared, with the same reason.
  - A PostgreSQL capture writes its `stream_state` row, with its record of dropped changes (empty or not), as soon as replication starts, not at its first commit: a quiet source's capture is on record from the start. The row holds no position, so where a capture resumes does not change.
  - A large statement on a skipped table, while other tables are captured, no longer raises "capture is effectively stopped ... run `bintrail snapshot`", whose remedy was MySQL's. While no table capture takes has had a change in the session, the alarm can still fire, and then gives the PostgreSQL remedy and says that a quiet table looks the same as none.
  - **Upgrading from 0.138.0 with tables that are not at `FULL`:** capture keeps running and takes the other tables; the changes of those tables from the upgrade on are not recorded. What 0.138.0 recorded of them stays in the history, and undo still refuses its `UPDATE`s and `DELETE`s. Their copy stays as the last update left it, fresh mode leaves them out, and a read of one of their rows at a past moment is refused. To capture such a table again, run the `ALTER TABLE` that `bintrail-pg doctor` prints (on each partition too, for a partitioned table), then a full read. A server that is stopped cannot be started from the web interface until then.
