- **PostgreSQL port: tables listed with commas, and `EXISTS (SELECT * ...)`, stay on the copy when a table holds a `char(n)` column nobody compares** (#3219). Two statements of the same family went to the source for a `char(n)` column they never used. A table with a `char(n)` column written as a later table of a `FROM` list with commas (`FROM orders, order_line WHERE ol_o_id = o_id`) was taken for the table's row used as a value; it is now read as the join it is, as the same statement written with `JOIN ... ON` already was. And the `*` of `EXISTS (SELECT * FROM t WHERE ...)` or `NOT EXISTS` was taken for a read of the padded column; PostgreSQL does not evaluate the select list of an `EXISTS`, and neither does the copy. Both were measured against PostgreSQL answering the same rows. What still goes to the source, measured answering otherwise: either statement when its `WHERE` compares the `char(n)` column itself, a `*` in any other subquery (`IN`, `= ANY`, a subquery used as a value or compared as a row), an `EXISTS` whose subquery has a `UNION`, `INTERSECT` or `EXCEPT`, `NATURAL JOIN` and `USING` over the column, and a list that mixes `JOIN ... ON` with commas, which the port does not follow.
