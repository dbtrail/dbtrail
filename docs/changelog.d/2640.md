- **The read of some tables alone, for such an update** (#2640, third part, first half). Internal for now: nothing calls it, so the daemon behaves as before. It reads the given tables from the source into a working folder, as finished files a snapshot update can take, or returns an error and no file at all. It declines, so that the caller takes a full read, under the `no-lock` and `safe-no-lock` lock modes, for a name with a comma or a dot, and for a schema mydumper cannot look up in a table list.
- **A snapshot update can fold from that read** (#2640, third part, second half). Internal for now: nothing asks for it, so the daemon behaves as before. The update reads the given tables, waits up to five minutes for capture to pass the point of that read, and folds every table of the server to one point. If capture does not get there, or a table is refused again, it publishes nothing. The working files are removed when the run ends, and by the next start if the process was killed.
- **A truncated table is read again alone, not the whole server** (#2640, fourth part). When a scheduled snapshot update is refused for tables changed by a statement that leaves no row changes to apply (a `TRUNCATE`, a table dropped and created again, a change of its columns), the schedule now reads only those tables from the source and brings every table of the server to one point, the others updated from the recorded changes, where it used to read the whole server (at most once a day). The Snapshots page says so for that run, and the daemon log names the tables and why each path was chosen. It does not count against, and is not held by, the limit of one full read a day. Everything else takes the full read as before: another reason for a refused table (a capture gap, a renumbered binary log, the catch-all `refused`), every table refused, a refused list cut short, a PostgreSQL server; and so does every way the read can end without a snapshot (capture not reaching it within 5 minutes, which is also what a source that writes nothing after the read gets, an error, the table refused again), with the same words and under the same daily limit. A table is read again alone once until an update goes through. On by default; `--baseline-reread-refused-tables=false` (`baseline-reread-refused-tables = false` in `dbtrail.cnf`, `BINTRAIL_BASELINE_REREAD_REFUSED_TABLES=false`) turns it off.
