- **The Rotation form refuses a retention under which table deltas can never work** (#2959). With table deltas on (the default), a table's changes are written beside its file only while the index keeps every change since that file was written, with a margin of one hour plus one update interval. A retention at or under two update intervals plus one hour (1h10m with an update every 5 minutes) ended every chain at the update after the one that began it, so every update wrote every table again in full, and the only trace was one INFO line per table. The Rotation form and `PUT /api/rotation` now refuse such a retention with 400, name the server whose schedule sets the limit, the shortest value that saves (`2h` for an update every 5 minutes) and the retention from which table deltas work on every update (`3h`: rotation drops whole hours, so just over the minimum most updates still write the tables in full), and say the way to a shorter one: turn table deltas off first, with `baseline-table-deltas = false` in `dbtrail.cnf`. The retention already in use is saved again as it is, so the interval and the future partitions can still be changed. Nothing changes with table deltas off, with no copy updated on a schedule that can run, or for updates a day apart or more: those write every table in full on any retention, so no retention is asked for.
- **A retention that is already too short for table deltas is said, not only logged per table** (#2959). The form cannot see every way there: `--rotate-retain` or `BINTRAIL_ROTATE_RETAIN` given to the daemon, a policy saved by an earlier version, a schedule made longer afterwards. For those, the Rotation form shows the finding in red when it opens (`GET /api/rotation` carries `deltas: {min_retain, recommended_retain, too_short, note}`), the server's **Update the copy** card on Snapshots says "Every update writes every table again in full" with the retention that schedule needs, and the daemon log carries one warning a day per server and schedule: `table deltas are on and the index retention leaves no room for them`. A server updated more than a day apart gets one grey line on that card instead, which asks for nothing. The daemon still starts and still updates the copy; this only says what each update costs.
- **Docs: how often a table is written in full** (#2959). `docs/dump-and-baseline.md` states when a chain of table deltas ends for a given retention and update interval, and `docs/console.md` the line the form refuses on and the retention it recommends.
