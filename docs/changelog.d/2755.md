- **SQL on the copy of a PostgreSQL source reads each column as its type** (#2755). A snapshot of a PostgreSQL source holds every value as text, and until now SQL on the copy saw text: `ORDER BY id` gave 1, 10, 11, 2; `max(amount)` gave 9.90 where the table held 1234.56; `sum()`, a comparison with a number or a date and `date_trunc` were refused; `city = 'Lima'` also matched `lima`; and `SELECT *` returned the columns sorted by name. The views now read whole numbers, `numeric`, `real`, `double precision`, `boolean`, `date`, `timestamp`, `timestamptz`, `uuid` and `bytea` as their types, compare text with regard to case, and list the columns in the table's order, from the shape each snapshot file already records. The files are not rewritten, so a snapshot taken by an earlier version gains the types too, as long as it records the table's shape; an older one reads as text until the next full snapshot. A views file that follows later snapshots keeps reading these tables as text. A `numeric` with no precision is an exact decimal with 18 decimals. A value its type cannot hold (`NaN` in a `numeric`, more digits than fit) fails the statement that reads it; it is never rounded or read as NULL. `json`, `jsonb`, `time`, `interval`, arrays, enums and extension types stay text (#2787), and NULL order and integer division still follow MySQL's rules (#2786). Of the 55 statements `internal/pgcompare` ran against PostgreSQL 14 to 17 before this change, 47 now answer as the source does, up from 26. See [how each type reads](postgres.md#how-each-type-reads-in-sql-on-the-copy).
