- **PostgreSQL: a snapshot update of a busy source no longer says the index follows another cluster** (#3044). An update from the recorded changes reads the newest change the index holds and then looks for the first change after the update's own time, and refuses when the second is later in the WAL than the first: on one cluster that cannot be, so the index must be following a restored or replaced one. Capture writes between the two reads, though, and on a source that commits all the time the change found could be one written after the "newest" was read. The update then published nothing, said `the index now follows another PostgreSQL cluster than the one the snapshot was taken from; take a new snapshot`, and the schedule read the whole source again instead; the next update worked. The two reads are now told apart by the order the changes were written in, and read again when the index moved between them. A source that really was replaced is refused as before, with the same message.
