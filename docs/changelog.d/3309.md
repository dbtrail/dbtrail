- **The MySQL port picks the copy's join order of a list of tables before it runs** (#3309, #3297). With read routing, CH-benCHmark Q5, Q8 and Q21 ran out of memory in the copy's own join order (after 237 s, 16 s and 7 s on a copy of 100 warehouses) and then went to MySQL, so they took longer than on MySQL alone. A routed `SELECT` whose `FROM` is a list of tables separated by commas now runs with the copy's join reordering off: in the order written when that order is connected already (each table has a condition with one before it), and otherwise written again, through the engine's own parser, with the largest table first and each next table the smallest one a condition joins to those placed. Q5 answered in 2.9 s, Q8 in 0.67 s and Q21 in 1.8 s; over the 22 reports every answer was the same and none was more than 1.6 times slower (Q3, 0.46 to 0.75 s). Any other shape (one table, an explicit `JOIN`, a subquery in `FROM`, `WITH`, an `OR` at the top of `WHERE`, `*`, `COLUMNS(...)`, `#n`) is planned as before, and a statement with `STRAIGHT_JOIN` in any form (as a join or as `SELECT STRAIGHT_JOIN`) is never reordered: the copy keeps the order written where it can, as before, and plans it as before where it cannot. A statement that fails in the order picked is not run again in another order and goes to MySQL as before. `/status` counts the copy's answers the client got this way per server under `join_orders`: `written`, `connected`, and `failed` when picking the order failed on an error (also logged as a warning) and the statement ran in the copy's own order. The port without routing and the PostgreSQL port are unchanged.
