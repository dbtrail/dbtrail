- **PostgreSQL router: a table whose capture dropped its changes is answered by your PostgreSQL, not from its old snapshot** (#3191). A table whose changes capture skips (a primary key declared `DEFERRABLE`, a table below `REPLICA IDENTITY FULL`), or after a lost slot, a capture record of dropped changes that does not say which tables or cannot be read, or a snapshot published over a known loss, was read by the copy from its snapshot alone, with nothing to say so: in fresh mode unless the connection had already read that table from the source, in fast mode always, since such a table keeps the snapshot of its last full read and the copy's age of a PostgreSQL server is not computed. This holds in fresh and in fast mode. A statement that reads such a table now goes to the source, which answers with its current rows. It is counted as `source` under `table_not_captured` in `SHOW dbtrail.router_status`, `/status` and the status line. A JOIN of such a table with others goes to the source whole. Whether a drop came after a table's snapshot is judged by WAL position (the snapshot's LSN against the drop's commit LSN), not by comparing the source's clock with DBTrail's. **What a client sees:** the current rows, where it used to get the snapshot's. A connection that cannot send anything to the source (no forwarding user, or a server that hides tables) is still answered by the copy, now with a NOTICE that names the table and when its snapshot was read, or that says DBTrail could not check; `SUMMARIZE` of such a table gets the same NOTICE. Unchanged: a table whose recent changes are not ready or are over a budget, a transaction block, and the copy's own commands (`SHOW TABLES`, `DESCRIBE`, and `SUMMARIZE` apart from its NOTICE).
