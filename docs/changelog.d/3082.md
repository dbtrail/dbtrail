- **PostgreSQL table deltas: each snapshot update writes the changes of its own window, and no longer rewrites every change since the table's file** (#3082). With PostgreSQL table deltas on, a changed table was published as its previous file and ONE pair of small files beside it holding every change since that file was written: each update read that pair, merged its window into it and wrote it whole again, so an update's time grew with the time since the file was written and not with what changed. Each update now writes a pair of its own window after the pairs before it (a chain), and links the pairs before into the new snapshot as they are. Every reader of the copy already read a chain in order (the views, fresh mode, the upload and its integrity checks), and fresh mode now starts a table's changes at the last pair's end instead of the first's. The chain is written into a new table file by the rules of the MySQL chain: when it is a day old, when its files together pass half of the table file (a chain under 1 MiB is left alone), before the index drops the changes the table file starts from, or when its numbering runs out. A single window no longer writes the table in full because it changed many rows: its pair is written, and the next update writes the table in full if the chain then passes the line, as MySQL does. A chain that is not whole beside the previous file (a pair missing in the middle, half a pair, a pair the snapshot's `_MANIFEST` names and is not there, or one there that it does not name) is never read as an older table: the update reads every change since the file again, as before, and starts a new chain. Each pair records how many rows the table holds, counted from the window's inserts and deletes; a count that does not add up is not recorded, and the next update counts again from the file.
