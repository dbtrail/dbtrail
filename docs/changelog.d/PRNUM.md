- **The PostgreSQL port serves a server only when it can forward** (#PRNUM). A connection that could reach only the copy got, for some statements, rows PostgreSQL would not return, with no error. Now a client of a PostgreSQL server the port cannot send to its PostgreSQL is refused at login with `FATAL` `08004`, naming the server, the reason and both ways to serve it: forward as the user DBTrail connects with (`server forward-user <server> --capture-account`, or the box in the server's form), or give it a forwarding user of its own. Forwarding as the user DBTrail connects with is now the default for a new PostgreSQL server: the box in the form is ticked, and `server add` with nobody at a terminal answers yes. The checks warn when that user is a superuser or can bypass row-level security, with the statements for a role that only reads. A saved forwarding user that is the user DBTrail connects with is used as that account once the server says yes, instead of being refused. Capture, snapshots, the web interface and the MySQL port are unchanged for every server; the daemon names at boot each server the port does not serve, its Overview has a card, and `GET /api/servers` has `pg_port_refused`.
  - **Before you upgrade**: a PostgreSQL server with no forwarding user and without a yes about the user DBTrail connects with stops being served by the PostgreSQL port: its clients get the error above at login. Run `bintrail-console server forward-user <server> --capture-account` (or tick the box in the server's form), or set a forwarding user of its own, before or right after the upgrade. Capture of that server keeps running either way.
