- **Fresh mode can wait for the source's position before it answers** (part of #2645). With `BINTRAIL_SQL_FRESH_WAIT` set (`SQL_FRESH_WAIT` in the compose `.env`; `on` is 200 ms, or a duration like `500ms`, up to `10s`), a statement on the SQL port whose tables all have tails first reads where the source's binary log stands, waits until capture's saved position reaches it, wakes the tails' update and waits for it, so a row a client wrote just before is in the answer. Past the limit it answers with what is ready, as before. The router reads the position with the account capture uses (`REPLICATION CLIENT`), one read shared by the statements that arrive while it runs; a refusal is said once in the log and shown in `/status`. A statement does not wait over a table with no tail, when capture is known to be behind, when the source's binary log is another one, or when capture saved no position. The router's `/status` gives per server `fresh_wait`: the limit, how many statements waited, reached the position, ran out, and why the others did not wait, and the median wait. Off by default; not yet a per-server choice. The compose file is version 10 (it passes `SQL_FRESH_WAIT` to the router).
