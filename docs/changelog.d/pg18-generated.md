- **PostgreSQL 18: a generated column no longer lets the setup DBTrail asks for stop your application** (`pg18-generated`). On PostgreSQL 18 a table at `REPLICA IDENTITY FULL` that belongs to a publication refuses every `UPDATE` and `DELETE`, from the source's own application too, when it has a generated column the publication does not publish; DBTrail asks for exactly that setup, and nothing said so. `bintrail-pg doctor`, the web interface's checks when a server is added, and the capture when it starts now find it and stop, with the statements to run: first the one that lets the application write again (`ALTER TABLE ... REPLICA IDENTITY DEFAULT`), then, for a `STORED` column, `ALTER PUBLICATION ... SET (publish_generated_columns = stored)`, with which capture, full reads, snapshot updates and recovery work (run end to end on PostgreSQL 18.7). A table with a `VIRTUAL` generated column, new in 18, cannot be captured, since PostgreSQL cannot publish it; the message says to take it out of the publication. Any publication the table belongs to counts, not only DBTrail's. The setup guide carries the warning before the step that asks for `REPLICA IDENTITY FULL`. PostgreSQL 17 and older have no such rule and are unchanged.
