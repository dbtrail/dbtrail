- **The PostgreSQL port announces PostgreSQL's whole number type for `length`, `position`, `strpos`, `ntile` and `sum`** (#3073). The port announced each result column with the type the copy computes it with, which for these is not PostgreSQL's: `sum()` of an `integer` or a `smallint` column came as a `numeric` instead of a `bigint`, and `length()`, `char_length()`, `position()`, `strpos()` and `ntile()` as a `bigint` instead of an `integer`. The value was right, but a driver that decodes by the announced type (pgx, JDBC) handed the application another type than the source does. They are now converted to PostgreSQL's type before the port answers, in text and in binary, also under an alias, in a subquery or a `WITH`, behind `SELECT *`, as a window, inside another expression, and in what a prepared statement announces before it runs. No value and no column heading changes. Measured on the wire against PostgreSQL 16, byte for byte. A statement that calls one of them in an item with no name of a subquery or beside a `*` keeps the copy's type for it: give the item a name (`AS n`). A `sum` whose value holds a prepared statement's argument with no cast (`sum(qty + $1)`) also keeps the copy's type. Not changed, and listed in `docs/postgres.md`: `extract` and `date_part` (a `bigint`; PostgreSQL has a `numeric` and a `double precision`), a lone `NULL` (an `integer`; PostgreSQL has `text`), a `date` less a `date`, and a `smallint` with a number.
