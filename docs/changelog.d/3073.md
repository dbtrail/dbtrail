- **The PostgreSQL port announces PostgreSQL's type for `length`, `sum`, `extract`, `date_part` and a lone `NULL`** (#3073). The port announced each result column with the type the copy computes it with, which for some expressions is not PostgreSQL's: `sum()` of an `integer` column came as a `numeric` instead of a `bigint`, `length()`, `position()` and `ntile()` as a `bigint` instead of an `integer`, `extract(year FROM x)` as a `bigint` instead of a `numeric`, `date_part('year', x)` as a `bigint` instead of a `double precision`, and `SELECT NULL` as an `integer` instead of `text`. The value was right, but a driver that decodes by the announced type (pgx, JDBC) handed the application another type than the source does. These are now converted to PostgreSQL's type before the port answers, in text and in binary, also under an alias, in a subquery or a `WITH`, behind `SELECT *`, as a window, inside another expression, and in what a prepared statement announces before it runs. Measured on the wire against PostgreSQL 16, byte for byte. Still different, and listed in `docs/postgres.md`: a `date` less a `date`, a `smallint` with a number, the `sum` of a name the statement defines itself, and a `NULL` named inside a subquery.
