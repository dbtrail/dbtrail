- **The PostgreSQL port runs a client's transaction blocks on the source** (#2771). `bintrail-console pg-router` answered every statement from the copy, so a `BEGIN` ... `COMMIT` read the copy as of its last update and the catalog statements it does not recognize were refused. Now a transaction block a client opens, every statement in it, and a catalog statement the copy does not answer run on the server's own PostgreSQL, as the server's forwarding user (`bintrail-console server forward-user <server> -u <user> -p`, or Forwarding user in the web interface's server form, now shown for PostgreSQL servers too), never as the user DBTrail captures with; without one, the port answers from the copy alone as before. A client holds at most one connection to the source, only while its block runs there (a connection pool's idle clients hold none), at most `--max-source-connections` (16) for the process (`53300` past it), and every wait for the source is bounded by the port's five-minute cap. It is read-only three ways: a statement that is not a read is refused before it is sent (`25006`), the connection is opened with `default_transaction_read_only = on` so PostgreSQL refuses a function that writes, and the port closes it if that setting is ever turned off (PostgreSQL 14 and later report it; an older source is not forwarded to). `COPY`, `LISTEN`, `NOTIFY`, `DO`, `set_config()`, advisory locks and `dblink` are refused by name. The source's rows, errors (with their code, detail and position), notices and cancel go through, in the simple and the extended protocol; a client that leaves in the middle of a statement has it cancelled on the source; the session's `TimeZone`, `search_path`, `statement_timeout` and output formats are set on the source first; TLS to the source follows the forwarding user's `sslmode`. A statement prepared outside the block and run inside it whose columns the copy had typed otherwise is refused with `cached plan must not change result type` instead of being read as the wrong value. A source that cannot be reached answers `08001`, one that refuses the forwarding user `08004`, and a lost connection `08006` until the client reconnects. Checked against PostgreSQL 16 with psql, pgx (every query mode), psycopg 3 and JDBC. The MySQL port is unchanged: it still does not forward to a PostgreSQL source.
